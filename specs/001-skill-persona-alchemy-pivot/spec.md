# Feature Specification: 金丹化性 · Skill-Persona Alchemy Pivot

**Feature Branch**: `001-skill-persona-alchemy-pivot`

**Created**: 2026-08-07

**Status**: Draft

**Input**: User description: "我要修改这个项目的开发重心, 这个功能核心的炼丹功能基于https://github.com/alchaincyf/nuwa-skill 实现, 不做rag了,主要做一个道人吃了多个金丹(skill)对于语言模式的变化,因为不同的人有不同的性格,有不同的金丹之后,这个人会发生什么化学变化,是这个项目要解决的问题"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 创建道人与服用金丹 (Priority: P1)

用户可以创建一个“道人”，为道人设定基础性格（如沉稳、跳脱、儒雅、狂放），然后将一个或多个“金丹（skill）”分配给道人。道人服用金丹后，其语言模式应发生可观测的变化：语气、用词、修辞、表达节奏、价值观倾向等都会随金丹组合而改变。

**Why this priority**: 这是项目的核心体验：性格 × 技能 → 语言化学变化。没有这一点，项目失去存在意义。

**Independent Test**: 可以独立测试通过 UI/API 创建道人、分配金丹、发送一条测试消息，观察返回文本的语气是否与基础性格和金丹描述一致。

**Acceptance Scenarios**:

1. **Given** 用户创建了一个性格为“沉稳”的道人，**When** 用户让道人服用“文言文金丹”，**Then** 道人回复应呈现沉稳、古雅、书面化的语言风格。
2. **Given** 同一道人已服用“文言文金丹”，**When** 再服用“赛博朋克金丹”，**Then** 回复应同时出现古雅与科幻元素的混合表达，而非只体现其中一个。

---

### User Story 2 - 炼制金丹 (Priority: P1)

用户可以基于 nuwa-skill 的机制“炼制”新的金丹。每颗金丹包含一套可影响语言模式的元信息（如风格描述、价值观、口头禅、禁忌、示例对话等），并可以被保存、复用、分享给其他道人服用。

**Why this priority**: 金丹是内容生产资料，必须可扩展、可复用，才能支撑长期玩法。

**Independent Test**: 可以独立测试通过炼丹界面填写金丹信息并保存，之后新道人可以服用该金丹并表现出对应风格。

**Acceptance Scenarios**:

1. **Given** 用户进入炼丹界面，**When** 填写金丹名称、风格描述、示例对话并保存，**Then** 系统持久化金丹并在金丹库中可见。
2. **Given** 用户创建了一颗名为“鲁迅风”的金丹，**When** 让道人服用后提问，**Then** 回复应带有尖锐、讽刺、白描式的语言特征。

---

### User Story 3 - 多金丹组合的涌现效果 (Priority: P2)

当道人同时服用多颗金丹时，系统应能模拟“化学反应”：不同金丹之间可能产生协同、冲突或中和效果，最终输出的语言模式不是简单拼接，而是融合后的涌现性格。

**Why this priority**: 这是项目的差异化体验，体现“化学变化”而非“模板叠加”。

**Independent Test**: 可以独立测试固定基础性格下，分别服用 A、B、A+B 三种组合，比较三种回复的差异，A+B 应体现出既非 A 也非 B 的新特征。

**Acceptance Scenarios**:

1. **Given** 道人基础性格为“跳脱”，**When** 同时服用“严谨逻辑金丹”与“嘻哈金丹”，**Then** 回复应在逻辑严密的同时带有轻松俚语，呈现独特张力。
2. **Given** 两颗金丹风格明显冲突，**When** 同时服用，**Then** 系统应能检测到冲突并给出一种合理的折中或摇摆表达（或提示用户冲突）。

---

### User Story 4 - 移除 RAG 相关功能 (Priority: P2)

原有基于文档上传、向量检索、RAG 对话的功能不再作为核心。相关数据表、服务、前端页面应被清理或降级，避免与新的金丹化性系统耦合。

**Why this priority**: 用户明确要求“不做 rag 了”，必须清理旧路径以聚焦新方向。

**Independent Test**: 可以独立测试删除 Qdrant 依赖、文档上传入口、RAG 对话路径，系统仍可正常运行核心功能。

**Acceptance Scenarios**:

1. **Given** 项目启动，**When** 检查 docker-compose 与服务注册，**Then** 不再依赖 Qdrant 向量数据库。
2. **Given** 用户进入前端，**When** 浏览主界面，**Then** 不再出现文档上传、知识库管理等 RAG 相关入口。

---

### Edge Cases

- 道人未服用任何金丹时，应仅体现基础性格。
- 金丹列表为空时，系统应提供默认示例金丹或引导用户炼丹。
- 多颗金丹风格完全相反时，系统应如何处理？（冲突消解策略）
- 同一颗金丹被同一道人重复服用，是否叠加效果？
- 用户删除一颗已被服用的金丹，道人的语言模式应如何回退？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 允许用户创建、编辑、删除“道人”，并为道人设定基础性格维度（如沉稳-跳脱、儒雅-粗犷、理性-感性等）。
- **FR-002**: 系统 MUST 允许用户基于 nuwa-skill 机制“炼制”金丹，每颗金丹包含风格描述、价值观、口头禅、禁忌、示例对话等字段。
- **FR-003**: 系统 MUST 支持一个道人服用多颗金丹，并将基础性格与所有金丹信息综合为统一的“语言模式配置”。
- **FR-004**: 系统 MUST 在对话时调用 LLM，并将综合后的语言模式配置注入系统提示词或等效机制，使回复体现融合后的语言风格。
- **FR-005**: 系统 MUST 移除 RAG 向量检索、文档上传、知识库管理等不再需要的功能，或将其标记为废弃。
- **FR-006**: 系统 MUST 持久化道人、金丹、服用关系等核心数据。
- **FR-007**: 系统 SHOULD 提供“试丹”功能：在不保存的情况下预览某颗或某组金丹的语言效果。
- **FR-008**: 系统 SHOULD 支持冲突检测与消解：当多颗金丹风格冲突时，给出提示或采用预定义策略（如优先级、随机摇摆、折中融合）。

### Key Entities *(include if feature involves data)*

- **道人 (Taoist/Persona)**: 代表一个 AI 角色。属性：基础性格维度、当前服用的金丹列表、语言模式快照、创建者。
- **金丹 (Skill/Golden Pill)**: 代表一套可影响语言模式的规则包。属性：名称、描述、风格标签、价值观、口头禅、禁忌、示例对话、作者、版本。
- **服用关系 (Consumption)**: 道人与金丹的多对多关系。属性：服用时间、剂量/权重、生效顺序。
- **语言模式 (Language Pattern)**: 由基础性格 + 金丹组合推导出的运行时提示词配置。可缓存、可版本化。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户可以在 3 分钟内完成一次“创建道人 → 炼制金丹 → 服用 → 对话体验”的完整流程。
- **SC-002**: 在盲测中，服用不同金丹组合的道人回复能够被人工区分出明显风格差异（准确率 > 70%）。
- **SC-003**: 系统不再依赖 Qdrant，容器启动时间减少 [NEEDS CLARIFICATION: 需要基准数据]。
- **SC-004**: 核心数据模型单元测试覆盖率不低于 70%。

## Assumptions

- 项目继续沿用 React + Go + Python 的微服务架构，但 Python 服务从 RAG 引擎转型为“炼丹/语言模式合成引擎”。
- LLM 调用继续通过 OpenAI 兼容 API 进行，模型选择由用户配置。
- nuwa-skill 提供了一种可借鉴的技能定义与组合机制，但具体集成方式需要进一步研究。
- 前端用户界面需要重新设计，以“炼丹炉”“金丹”“道人”等道教隐喻为核心交互语言。
- 移除 RAG 功能时不迁移历史文档数据；如有需要，后续单独处理。

## Open Questions / Needs Clarification

- **NEEDS CLARIFICATION**: nuwa-skill 的具体架构、数据格式、组合算法是什么？需要研究其仓库后确定集成方式。
- **NEEDS CLARIFICATION**: 多金丹冲突消解策略应由产品定义：优先级、权重、随机、折中，还是交给 LLM 自行融合？
- **NEEDS CLARIFICATION**: “语言模式变化”是否需要量化评估（如风格分类器、嵌入相似度），还是仅依赖人工盲测？
- **NEEDS CLARIFICATION**: 是否保留原有用户、会话、消息等数据模型，还是完全重写？
- **NEEDS CLARIFICATION**: 金丹之间是否有“相生相克”的显式规则，还是完全依赖 LLM 的隐式融合？
