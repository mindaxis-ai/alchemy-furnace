# LangGraph 语义导演与 Humanizer 设计

**状态：** 已批准，待实现

**日期：** 2026-09-08

**范围：** 炼丹炉桌面版单聊与群聊的模型生成链路，以及中英文 README

## 1. 目标

人物回复需要同时满足三件事：听懂用户真正想问什么，根据问题分量决定该说多少，并以符合人物性格和所获能力的自然语言回答。

当前 LangGraph 链路只把静态人物提示词、历史和记忆交给模型。它没有完整的语义理解、回复预算和生成后编辑阶段，导致模型容易退回通用助手习惯：小问题长答、机械分点、套话开场、重复总结和无必要的追问。

本设计把一次回答拆成四个职责明确的阶段：

```text
用户原始 Query + 有界历史
        ↓
语义理解层（默认模型，一轮一次）
        ↓
导演层（确定性预算，一轮一次）
        ↓
人物生成层（当前人物模型，每位发言人一次）
        ↓
Humanizer 层（当前人物模型，每位发言人一次）
        ↓
校验、完整边界收束、最终输出与持久化
```

Humanizer 作为自然表达基线，人物性格、能力带来的表达特征和真实示例对白拥有更高的风格优先级。它不能把不同人物改成同一种口吻。

## 2. 设计原则

- Python/LangGraph 继续拥有语义理解、导演计划、提示词编译和模型调用；Go 继续拥有业务数据、凭据、最终消息持久化和公共 SSE 映射。
- 原始 Query 始终作为最后一条 `user` 消息进入人物模型。语义层不替用户改写问题。
- 语义理解调用系统默认模型，每轮只执行一次；群聊成员共享同一份理解。
- 导演层读取语义结果并用确定性规则计算预算，不增加第四次模型调用。
- 人物原稿和 Humanizer 都使用该人物的模型、身份、能力和少量示例对白。
- Humanizer 只编辑表达，不增加事实、观点、数字、名字、链接、引用或代码，不删除完成任务所必需的信息。
- 普通小问题默认短答。用户明确要求详细、步骤、清单、文章或代码时才展开。
- 中间语义、原稿和 Humanizer 输入不写入业务消息表，不进入普通日志，也不通过公共 SSE 暴露。
- 任一附加阶段失败时使用可预测的降级路径，保证对话可用。

### 产品隐喻与人物身份边界

“炼丹炉、道人、金丹”首先属于产品界面、数据模型和能力组合隐喻，不属于人物的身份或默认世界观。运行时提示词必须把 Agent 描述为一个具体的人，把金丹效果翻译成人物已经掌握的知识、思维方式、价值倾向和语言习惯。同时，人物应知道自己在产品内服用过哪些金丹；这是用户可能询问的既定记录。

- 人物不自称“道人”，不把“丹性”“修炼”当作自我本质，也不主动谈幕后配置。
- 用户询问“吃了什么丹、有哪些金丹”时，人物可以按产品记录如实回答具体名称；平常回答不主动搬出这些记录。
- 系统不因产品采用中式炼丹外壳而默认人物使用古风、道教或修仙口吻。
- 只有人物资料或示例对白本身明确具有古风、宗教或炼丹背景时，相关表达才可以出现。
- 现有 Go/Python 类型名、数据库字段和界面名词可以继续保留，本次不做大规模重命名；模型可见文本不得直接暴露这些技术和产品隐喻。

## 3. 语义理解层

### 3.1 输入

语义层输入包括：

- 当前用户原始 Query。
- 最近 6 条有效用户/人物消息，每条最多 1200 个 Unicode 字符。
- 会话类型和可用成员的非敏感摘要。
- 用户显式 `@`、停止、继续、报数等确定性指令识别结果。

确定性指令仍由现有规则优先处理。语义模型不得改变 `@` 命中、报数顺序、停止或继续语义。

### 3.2 输出契约

语义模型只输出通过 Pydantic 严格校验的结构：

```python
class SemanticUnderstanding(BaseModel):
    source: Literal["model", "fallback"]
    intent: Literal["casual", "vent", "factual", "advice", "task", "deep_dive"]
    core_request: str                 # 最多 400 字符
    emotion: Literal["neutral", "positive", "sad", "frustrated", "angry", "anxious"]
    complexity: Literal["tiny", "simple", "moderate", "complex"]
    detail_preference: Literal["brief", "normal", "detailed"]
    requested_chars: int | None       # 用户明确指定时填写，范围 80～8000
    format_preference: Literal["plain", "list", "steps", "code", "creative"]
    wants_advice: bool
    wants_follow_up: bool
    should_clarify: bool
    avoid_behaviors: list[Literal["lecture", "repeat", "summary", "list", "follow_up"]]
```

`core_request` 是模型对真实需求的短摘要，只作为带明确边界的参考信息。所有控制行为只能来自校验后的枚举和布尔字段，不能把模型生成的自由文本当作系统指令执行。

### 3.3 提示注入防护

- 原始 Query 以普通用户消息提供给语义模型，并被明确标记为待分析数据。
- 语义输出拒绝未知字段，字符串和列表均有长度上限。
- 语义层不能产生工具调用、系统提示、模型名称或凭据字段。
- `core_request` 注入人物上下文时使用数据分隔符，并声明它是参考解释，不具有指令优先级。

### 3.4 降级

默认模型缺失、超时、输出非法或服务异常时，使用本地保守分类器：显式“详细”进入 `deep_dive`，明确倾诉进入 `vent`，任务动词进入 `task`，疑问词进入 `factual`，其余进入 `casual`。降级结果标记 `source=fallback`，但不向用户显示错误。

## 4. 导演层

导演层是纯函数。它读取 `SemanticUnderstanding`、显式用户约束、会话类型和确定性指令，生成 `ResponseBudget`：

```python
class ResponseBudget(BaseModel):
    target_chars: int
    max_chars: int
    max_sentences: int
    max_tokens: int
    allow_list: bool
    allow_follow_up: bool
    max_speakers: int
```

默认预算如下。字符数按 Unicode 字符计算，Token 上限用于模型调用，字符和句数用于最终校验。

| 意图 | 目标字数 | 硬上限 | 句数 | Token | 列表 | 群聊人数 |
|---|---:|---:|---:|---:|---|---:|
| `casual` | 40 | 120 | 2 | 128 | 否 | 1 |
| `vent` | 60 | 120 | 2 | 128 | 否 | 1 |
| `factual` | 120 | 220 | 3 | 256 | 默认否 | 1 |
| `advice` | 180 | 320 | 4 | 384 | 必要时 | 1 |
| `task` | 320 | 800 | 8 | 768 | 允许 | 2 |
| `deep_dive` | 600 | 1600 | 12 | 1400 | 允许 | 2 |

覆盖顺序固定为：安全边界、用户明确要求、确定性指令、语义意图默认值、人物表达偏好。

- “简短、只说结论、别展开”把硬上限压到 120 字和 2 句。
- “详细、深入分析”允许使用 `deep_dive` 预算。
- 用户指定字数时，以 80～8000 字范围内的用户数值为目标。代码和结构化文件任务不按字符硬截断，只使用 Token 上限并保证内容结构完整。
- 用户要求“每人一句”时，群聊人数按明确点名确定，每位最多 1 句。
- 表达欲只影响群聊主动参与和一次自然追问的倾向，不能扩大单条回答预算。
- 语义层判断需要澄清时，导演预算为 1 个简短问题，不允许先写长篇假设。

## 5. 人物生成层

人物模型输入顺序为：

1. 安全与身份边界。
2. 人物的姓名、基础性格、语言习惯、价值观、知识能力和诚实边界；另附一个边界明确的产品事实区，列出已服用金丹名称，仅供用户询问时如实回答，不作为身份或语言风格指令。
3. 语义理解的受限结构化摘要。
4. 导演计划与硬预算。
5. 最多两组与当前人物相关的示例对白，作为真实 `human/assistant` 消息。
6. 有界会话历史和记忆。
7. 当前用户原始 Query，作为最后一条 `human` 消息。

示例对白按能力权重和启用顺序稳定选择，总计不超过 400 字符。示例的作用是提供具体语感；Humanizer 规则不得覆盖示例中有意保留的排比、反讽、口语、省略或时代化表达。

模型调用必须接收导演层计算的 `max_tokens`。人物原稿只保存在当前 LangGraph 运行状态中，不立即产生公共 `assistant_delta`，也不写入 Go 消息表。

## 6. Humanizer 层

### 6.1 运行方式

Humanizer 使用当前人物模型做第二次编辑。输入包含原始 Query、语义摘要、导演预算、人物身份与能力表达规则、选中的示例对白和人物原稿。输出只能是最终正文。

规则基于已安装的 MIT License `humanizer` skill，并在项目内固化为运行时提示策略，不依赖用户机器上的 Codex 技能目录。实现时将原作者和 MIT 许可写入 `THIRD_PARTY_NOTICES.md`。

### 6.2 编辑规则

Humanizer 应优先处理以下 AI 痕迹：

- 删除“这是个好问题”“当然可以”“下面让我们深入看看”等舞台式开场。
- 删除没有真实对比价值的“不只是 X，而是 Y”。
- 删除重复上一段的一句话总结和“希望这能帮到你”式收尾。
- 避免机械的三段式、强行排比和重复句首；人物示例有意使用时除外。
- 普通闲聊、倾诉和简单事实问题不使用标题、列表、总结。
- 删除空泛的意义拔高、营销词和没有来源的“专家认为”。
- 不默认使用“首先、其次、最后、综上所述、值得注意的是”。
- 不主动追加“如果你愿意，我还可以……”；只有语义层确认用户期待追问时才允许一个自然问题。
- 保留原稿中的事实、数字、专名、URL、代码、引用、结论和真实不确定性。
- 保持人物的第一人称立场、词汇、节奏、幽默和能力，不把角色改成中性客服，也不擅自加入古风或炼丹措辞。
- 小问题的改写只能等长或更短；任务型回答可以重组，但不能超过导演硬预算。

### 6.3 校验与降级

Humanizer 输出需要通过：非空、字符上限、句数上限、代码围栏平衡、URL 与明显数字保留、无系统提示泄漏。校验失败时最多重试一次；仍失败则使用人物原稿，并优先按完整句或完整列表项边界收束。普通文本在范围内没有完整边界时按 Unicode 字符截取并添加省略号；代码块不使用字符硬截断。

最终只有通过校验的文本产生 `assistant_delta` 和 `assistant_final`。Go 只持久化 `assistant_final`。

## 7. 群聊行为

语义理解与导演计划每轮共享一次。确定性 `@`、全体、报数、停止和继续规则保持现状。

- 普通闲聊、倾诉、事实和建议默认只选择一位最合适的人物。
- 任务和深入讨论最多选择两位，除非用户明确点名更多人。
- 导演同时给出总预算和每位预算，避免两个人物各写一篇完整长文。
- 每位人物独立生成原稿并独立 Humanize，使用自己的模型、性格、能力和示例。
- Humanizer 不能代替其他人物发言，也不能改变报数编号、`@` 目标或发言顺序。

## 8. 流式体验、成本与延迟

一次单聊正常需要三次模型调用：语义理解、人物原稿、Humanizer。开放式群聊还保留现有的一次 Supervisor 发言规划调用；语义调用每轮共享一次，每位发言人各有原稿和 Humanizer 两次调用。明确点名、全体和报数等确定性路径不需要 Supervisor 调用。

界面只展示 Humanizer 后的最终文本，不先显示原稿再替换。当前 LangGraph 已使用 `ainvoke` 获取整段模型结果，本设计不会进一步削弱现有流式能力；最终文本可以按自然片段发送公共 SSE，以维持逐步出现的视觉反馈。

README 必须明确说明更自然的回答会增加首字等待时间和模型调用量。未来可以增加“快速模式”，但不属于本次范围。

## 9. 错误处理与可观测性

阶段降级顺序：

1. 语义模型失败：本地分类器生成保守语义。
2. 导演层永远是纯函数，不因模型失败而不可用。
3. 人物原稿失败：沿用现有单人物失败与群聊跳过语义。
4. Humanizer 失败：使用通过预算收束的人物原稿。
5. 最终校验无法产生非空正文：返回现有可重试错误，不保存空消息。

普通日志只记录阶段、耗时、意图枚举、预算、输出字符数、降级原因和模型标识，不记录 Query、语义自由文本、原稿、终稿、完整提示词或凭据。Prompt Debug 明确开启时可以展示分阶段消息，但继续执行现有凭据脱敏。

## 10. 数据与接口变化

Python 线格式增加：

- `SemanticUnderstanding`
- `ResponseBudget`
- `ConversationState.semantic_understanding`
- `ConversationState.response_budget`
- `ConversationState.draft_reply`
- `AgentSnapshot.example_dialogues`
- 可用的 `default_model_ref` 运行时接线

Go 的编排快照从现有 `LanguagePattern.BehaviorProfile` 中稳定提取少量示例对白并发送，不修改数据库结构。凭据仍只存在运行期上下文，不进入检查点。

现有静态行为提示词也需要去除模型可见的“道人身份、永久丹性核心、金丹”等产品术语，改写为普通人物的“身份、稳定性格、知识与能力、语言习惯”。行为档案缓存版本随之提升，确保旧提示词自动重建。

LangGraph 在单聊和群聊共用的顶层路径中增加 `understand_turn`、`direct_response` 节点，在每位人物子图中增加 `humanize_reply`、`validate_final_reply` 节点。

## 11. 测试与验收

所有实现严格按 TDD：先观察目标测试失败，再写最小实现。

### 单元测试

- 语义输出严格校验、非法输出降级、提示注入输入不改变控制字段。
- 六种意图的默认预算、用户明确长度覆盖、澄清问题预算。
- 小问题不超过 120 字和 2 句；事实直答不超过 220 字和 3 句。
- Humanizer 删除套话、机械结构和重复收尾，同时保留数字、URL、代码和角色标记。
- 示例对白选择稳定、最多两组、总计不超过 400 字符。
- Humanizer 超时、空输出、超预算和围栏损坏时回退原稿。
- 群聊共享一次语义结果，并遵守默认发言人数。
- Go/Python 请求契约、检查点恢复、Prompt Debug 和最终消息幂等持久化。

### 固定行为评测

- “今天天气真不错”：1～2 句，无标题和总结。
- “什么是 API Key”：第一句直答，最多 3 句。
- “我今天好烦，只想吐槽”：先接情绪，最多 2 句，不列建议。
- “帮我排查构建失败”：允许必要步骤，不写空泛开场。
- “详细分析这套架构”：允许结构化展开，但先给结论。
- 鲁迅式人物与小新式人物回答同一问题：内容意图一致，词汇、节奏和立场可明显区分，且都不因产品外壳自称道人。
- 五人物群聊问一个小问题：默认只有一位回答。

最终需要运行 Python、Go、前端全量测试，并以 Wails 桌面版完成真实配置模型的人工验收。浏览器开发模式不能替代桌面验收。

## 13. 非目标

- 不把 Codex 或本地技能目录作为桌面运行时依赖。
- 不增加云端服务、常驻外部代理、RAG、工具调用或新的数据库表。
- 不让 Humanizer 修改事实正确性、替代人物推理或负责安全审核。
- 不提供关闭语义层或 Humanizer 的 UI 开关。
- 不恢复已删除的旧 Go `turnpolicy` 编排链路。
- 不扩展独立网页部署、移动端或新的桌面平台。
